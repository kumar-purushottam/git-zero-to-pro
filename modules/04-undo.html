Undo changes: restore, reset, revert

Made a mistake? Pick the right undo for where the mistake is right now: in your files, in staging, or in a commit.

Learning goals

  • Pick the right undo in seconds with one decision chart
  • Throw away edits you haven't staged with git restore
  • Unstage a file with git restore --staged
  • Fix your last commit with git commit --amend
  • Undo a commit safely with git revert, and know when git reset is dangerous

The idea

There is no single "undo" in Git. The right command depends on where the mistake is now, and on whether you have already pushed it.

Which undo do I need?

Start at the top and follow your answers. You end at the right command.

  Is the mistake inside a commit?
  │
  ├─ no ──► Is it staged?
  │          ├─ yes ─► git restore --staged <file>    staging undone, edits kept
  │          └─ no ──► git restore <file>             edits are thrown away
  │
  └─ yes ─► Already pushed?
             ├─ no ──► git commit --amend             fix the last commit
             │         git reset --soft HEAD~1        or undo it, keep changes

git reset has three strengths. All of them undo the commit. They differ in what happens to your changes:

FlagStaging areaYour files
--softChanges stay stagedKept
--mixed (default)ClearedKept
--hardClearedThrown away

Commands

git restore notes.md

Throws away unstaged edits to a file and puts back the last saved version. Those edits are gone for good.

git restore --staged notes.md

Takes a file out of staging. Your edits stay in the file.

git commit --amend -m "docs: better message"   # fix the last message
git add forgotten.md
git commit --amend --no-edit                   # add a forgotten file to the last commit

Replaces your last commit with a corrected one. Only do this before pushing.

git revert a1b2c3d --no-edit

Makes a new commit that undoes commit a1b2c3d. History stays intact, so this is the safe choice for shared branches.

git reset --soft HEAD~1      # undo last commit, keep changes staged
git reset --hard HEAD~1      # undo last commit AND throw its changes away

HEAD~1 means "one commit before where I am". Use --hard only when you are sure.

Hands-on lab: rescue missions

Each mission makes a small mistake on purpose. Your job is to rescue it with the right command from the chart above.

  1. Base camp. Set up a repo with one commit. 
    mkdir -p ~/git-playground/m04 && cd ~/git-playground/m04
git init -q
echo "line one" > notes.md
git add notes.md && git commit -q -m "docs: add notes"

    No output (-q means quiet).

  2. Mission 1: the bad edit. Break the file, then rescue it. 
    echo "oops" >> notes.md          # the mistake
git restore notes.md                # the rescue
cat notes.md
line one

    "oops" is gone. Chart path: not in a commit → not staged.

  3. Mission 2: staged by accident. A secret file gets swept in by git add . 
    echo "password=1234" > secrets.txt
git add .                           # the mistake
git status -s
A  secrets.txt
git restore --staged secrets.txt    # the rescue
rm secrets.txt
git status -s

    The last git status -s prints nothing. The secret was never committed.

  4. Mission 3: the typo commit. It's not pushed yet, so amend it. 
    echo "line two" >> notes.md
git commit -q -a -m "docs: add line tow"         # the mistake (-a stages changed tracked files)
git commit -q --amend -m "docs: add line two"    # the rescue
git log --oneline
b7c8d9e (HEAD -> main) docs: add line two
a1b2c3d docs: add notes

    Still two commits. The typo commit was replaced, not added to.

  5. Mission 4: already pushed. Pretend "line two" is on GitHub and your teammates have it. Undo it safely. 
    git revert HEAD --no-edit           # the rescue
cat notes.md
line one

    The line is gone, and git log --oneline shows a new Revert "docs: add line two" commit. Nothing was erased.

  6. Mission 5: messy commits. Two "wip" commits, not pushed. Turn them into one clean commit. 
    echo "a" >> notes.md && git commit -q -a -m "wip 1"
echo "b" >> notes.md && git commit -q -a -m "wip 2"    # the mistake
git reset --soft HEAD~2             # the rescue: undo 2 commits, keep the changes staged
git commit -q -m "docs: add a and b"
git log --oneline -2
9a8b7c6 (HEAD -> main) docs: add a and b
f0e1d2c Revert "docs: add line two"

    One clean commit where there were two "wip" commits.

At work

Morning. You commit a config change, then notice it includes a real API key. You haven't pushed. Following the chart (in a commit → not pushed), you run git reset --soft HEAD~1, remove the key, and commit again. The key never left your laptop.

Afternoon. A teammate's merged change breaks the build on main, and everyone has already pulled it. Chart: in a commit → pushed. You run git revert <id> and push. The build is green again within minutes, and nobody's history was rewritten.

If a secret was ever pushed, git revert does not remove it. It's still in the history. Treat it as leaked and replace the key right away.

Common mistakes

Using --amend or git reset on a commit you already pushed.

Follow the chart. Once a commit is pushed, the answer is always git revert.

Running git reset --hard with work you never committed. That work is lost for good.

Run git status first. Commit or stash (Module 11) anything you want to keep.

Thinking git revert erases a pushed password or key.

Revert only adds an undo commit, so the secret stays in history. Replace the key immediately.
