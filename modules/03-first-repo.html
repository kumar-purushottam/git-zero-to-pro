Your first repo: init, add, commit

Create a repository, save your first snapshots, and read the history. These are the commands you'll use every single day.

Learning goals

  • Turn any folder into a repository with git init
  • Read git status and know what each file state means
  • Choose changes with git add and save them with git commit
  • See exactly what changed with git diff
  • Read the history with git log and write commit messages people can understand

The idea

git init creates a hidden folder called .git inside your project. That hidden folder is the repository. It holds every snapshot and every branch. Your files stay where they are. If you delete .git, your files remain but all the history is gone.

The life of a file

Git puts every file in one of four states. You move files between states with two commands:

  untracked ──git add──► staged ──git commit──► committed
                           ▲                        │
                           │ git add                │ you edit the file
                           │                        ▼
                           └─────────────────── modified
StateMeaningIn git status -s
UntrackedA new file Git has never saved??
StagedPicked for the next commitA  (new) or M  (changed)
CommittedSaved in history and unchanged since(not listed)
ModifiedChanged since the last commit, not yet staged M

Why have a staging step at all? It lets you choose. If you fixed a bug and also tidied an unrelated file, you can stage only the bug fix and commit it with its own message. Then commit the tidy-up separately.

What a commit really is

  a1b2c3d    ◄ ID: a unique fingerprint for this snapshot
  Author     Your Name <you@example.com>
  Date       Sat Nov 7 11:05 2026
  Parent     9f8e7d6    ◄ the commit that came before
  Message    docs: add first note
  Snapshot   every tracked file, exactly as it was

Because each commit points to its parent, commits form a chain. Your branch name, main, simply points at the newest one:

  9f8e7d6 ◄── a1b2c3d ◄── e4f5a6b   main ◄ HEAD (you are here)

Commit messages people can read

BadGood
updatedocs: add install steps for Windows
fixfix(cart): stop total going below zero
asdffeat(login): remember me checkbox

Write the subject as a short command, under about 50 characters: "add", "fix", "remove", not "added" or "fixing". This project uses the type(scope): what style, called Conventional Commits.

Commands

git init

Turns the current folder into a repository by creating the hidden .git folder.

git status          # full explanation of every file
git status -s       # short version: one line per file

Shows what's untracked, modified and staged. Run it before and after everything else.

git add notes.md    # stage one file
git add .           # stage everything in this folder (check git status first!)
git add -p          # go through changes piece by piece: y = stage, n = skip

Moves changes into the staging area, ready for the next commit.

git commit -m "docs: add notes file"

Saves everything that's staged as one snapshot, with your message. Without -m, Git opens your editor so you can type the message.

git diff            # changes you have NOT staged yet
git diff --staged   # changes that WILL go into the next commit

Shows changed lines: + for added, - for removed. Always check this before you commit.

git log                      # full history, newest first (press q to quit)
git log --oneline            # one line per commit
git show a1b2c3d             # one commit in detail, with its changes

Reads the history. The 7-character IDs are enough to name any commit.

Hands-on lab

You'll make a tiny repo with two commits. Your commit IDs will be different from the ones shown, and that's expected.

  1. Create a folder and turn it into a repository. 
    mkdir -p ~/git-playground/m03 && cd ~/git-playground/m03
git init
Initialized empty Git repository in /home/you/git-playground/m03/.git/
ls -a
.  ..  .git

    A hidden .git folder. That folder is your repository.

  2. Make a file and ask Git about it. 
    echo "# My notes" > notes.md
git status -s
?? notes.md

    ?? means untracked: Git sees the file but isn't saving it.

  3. Stage it, then commit it. 
    git add notes.md
git status -s
A  notes.md
git commit -m "docs: add notes file"
[main (root-commit) a1b2c3d] docs: add notes file
 1 file changed, 1 insertion(+)

    root-commit means this is the very first commit, so it has no parent.

  4. Change the file and look at the difference. 
    echo "Git saves snapshots, not just files." >> notes.md
git status -s
 M notes.md
git diff
@@ -1 +1,2 @@
 # My notes
+Git saves snapshots, not just files.

    M (with a space first) means modified but not staged. The diff shows your new line with a +.

  5. Stage it, check what will be committed, and commit. 
    git add notes.md
git diff --staged
git commit -m "docs: add first note"

    git diff is now empty, because everything is staged. git diff --staged shows the line instead.

  6. Read your history. 
    git log --oneline
e4f5a6b (HEAD -> main) docs: add first note
a1b2c3d docs: add notes file

    Two commits, newest at the top. HEAD -> main means you are on main, at its newest commit.

At work

You're fixing a login bug. While you're in the code, you also rename a few variables in another file and leave a debug print behind. Before committing, you run git status and git diff and spot all three changes.

You remove the debug line, stage only the bug-fix file with git add src/login.js, and commit it as fix(login): accept emails with capital letters. Then you commit the rename separately. A week later the rename turns out to break a report. The team undoes just that one commit, and the bug fix stays. Small, focused commits made that possible.

Common mistakes

Running git add . without looking, and committing junk files, build output, or a file with passwords.

Run git status first and add files by name. Module 12 shows how .gitignore keeps junk out automatically.

Commit messages like "update", "changes" or "final". Nobody, including you next month, can tell what they did.

Say what changed and where: fix(cart): stop total going below zero.

Expecting git commit to include edits you didn't git add.

Only staged changes go into a commit. Check git status right before committing. Anything still listed as modified will be left out.

Running git init in your home folder by mistake, so every file you own looks "untracked".

Check where you are with pwd before git init. If it already happened, delete only that new .git folder, and double-check the path before you delete anything.

Quick quiz

You run git add notes.md, then edit notes.md again, then commit. What gets committed?

The version from when you ran git add. The newer edit is still "modified". Run git add again to include it.

What is the difference between git diff and git diff --staged?

git diff shows changes you have not staged yet. git diff --staged shows what is staged, which is exactly what the next commit will contain.

What happens if you delete the .git folder?

Your current files stay, but every commit, branch and bit of history is gone. The folder is no longer a repository.

Summary

  • git init creates the .git folder, and that folder is the repository.
  • Files move: untracked or modified → git add → staged → git commit → committed.
  • Check before you commit with git status and git diff --staged.
  • Each commit has an ID, an author, a parent and a message. git log --oneline lists them.
  • Keep commits small and focused, and messages clear.
